Chronological record of what was done for each milestone, problems hit along the way, and how they were fixed. Written as work happens — see the implementation plan for the overall milestone breakdown.

## Milestone 1 — Scaffold + navigation

**What was done**
- Scaffolded the project with `create-expo-app` (Expo SDK 57, React Native 0.86, React 19.2.3, TypeScript).
- Installed and configured Expo Router (file-based navigation), React Native Reanimated 4, Gesture Handler, and `expo-dev-client`.
- Built the navigation shell: root layout, `(tabs)` with Deck/Trash/Settings placeholder screens, Onboarding and Tip Jar as modals.
- Converted `app.json` to `app.config.ts`, set up strict TypeScript with the `@/*` path alias.
- Wrote `PREREQUISITES.md` and `README.md`.
- Built and installed the dev client on a physical Android phone over USB.

**Problems hit & fixes**

1. **`npm install` peer dependency conflict** (expo-router pulls in web-only `@expo/ui`/`vaul`/`@radix-ui` packages requiring a newer `react-dom` than the pinned `react` version). → Added `.npmrc` with `legacy-peer-deps=true`.
2. **Reanimated 4 missing `react-native-worklets`** — the Babel plugin moved to a separate package in Reanimated 4; bundling failed with `Unable to resolve module react-native-worklets`. → `npx expo install react-native-worklets`.
3. **No Android SDK on the machine** — first-time setup. → Installed Android Studio via `winget`, then the Android 36 platform + Command-line Tools via the SDK Manager (the Standard install only included the newest platform, 37, not the one this project's `compileSdkVersion` needs).
4. **`JAVA_HOME` not set** — Gradle couldn't find `java`. → Initially pointed at Android Studio's bundled JBR, but see next point.
5. **JDK 25 (Android Studio's bundled JBR) breaks native builds** — `react-native-worklets`/`react-native-screens`'s `configureCMakeDebug` tasks failed with a cryptic `WARNING: A restricted method in java.lang.System has been called`, actually an Android Gradle Plugin bug where JDK 24+'s new native-access warning gets misparsed as a fatal error by AGP's Prefab tool. → Switched to **JDK 17** (downloaded via Android Studio's Gradle JVM criteria setting, which pulled Eclipse Temurin 17 into `~/.gradle/jdks/`), and pointed `JAVA_HOME` there instead.
6. **Antivirus (Norton) HTTPS interception breaks Java downloads** — Gradle/JDK couldn't download the Gradle distribution or Maven dependencies (`PKIX path building failed`), because Norton's "Web/Mail Shield" re-signs HTTPS traffic with its own root cert, which Windows trusts but each JDK's own separate `cacerts` trust store does not. → Exported Norton's root cert from the Windows certificate store and imported it into **every JDK's `cacerts`** used for building (Android Studio's JBR needed an elevated `keytool` call since it lives under `Program Files`; the user-profile JDK 17 didn't).
7. **A leftover `android/gradle/gradle-daemon-jvm.properties` pinned `toolchainVersion=25`** (auto-generated by an Android Studio IDE sync attempt), overriding `JAVA_HOME` entirely and re-triggering the JDK 25 bug regardless of environment variables. → Edited the file to `toolchainVersion=17`, then `gradlew --stop` to force a fresh daemon.
8. **Dev client couldn't auto-discover the running Metro server over USB** ("Fetch development servers" found nothing). → Entered `http://localhost:8081` manually in the dev client, which works because `adb reverse tcp:8081 tcp:8081` forwards the phone's localhost to the PC over USB.

**Checkpoint:** App runs on the physical Android phone via USB, dev client connects to Metro, empty tab navigation works. ✅

## Milestone 2 — Media Library service + permissions

**What was done**
- Installed `expo-media-library` and `expo-image`.
- Discovered this SDK version of `expo-media-library` ships a redesigned class-based API (`Query`/`Asset`/`Album`) replacing the old free-function API (`getAssetsAsync`/`getAssetInfoAsync`/`deleteAssetsAsync`, which now throw unless imported from `expo-media-library/legacy`) — read the installed package's own `.d.ts` files directly rather than trusting doc summaries, since this is a very recent change.
- Wrote `src/services/mediaLibrary.ts`: `checkPermissions`/`requestPermissions` (thin wrappers), `fetchAssetsPage` (offset/limit pagination via `Query`, sorted newest-first via `orderBy({ key: CREATION_TIME, ascending: false })`, using the cheap `exeForMetadata()` for listing), `resolvePlayableUri` (`new Asset(id).getUri()`), `deleteAssetsBatch` (`Asset.delete(assets[])`, batches into a single native confirmation).
- Added the `expo-media-library` and `expo-image` config plugins to `app.config.ts` (permission strings, `granularPermissions: ['photo', 'video']` — no audio).
- Built a temporary debug grid in the Deck tab (`AssetThumbnail` + `FlatList`) to validate the whole pipeline against real photos/videos on-device. This will be replaced by the real swipe deck in Milestone 3/4.

**Problems hit & fixes**

1. **Media permissions never actually declared in the manifest** — after adding `expo-media-library` and rebuilding, the Deck screen reported "0 recent items" with no permission prompt ever shown, and Android's app settings confirmed "no permission has been requested". Root cause: the `android/` native project had been generated in Milestone 1 (before `expo-media-library` existed), and the incremental prebuild step run by `expo run:android` didn't inject the new plugin's manifest permissions into the already-existing `AndroidManifest.xml`. → Deleted the whole `android/` folder (it's gitignored/fully generated) and rebuilt from scratch, which correctly wrote `READ_MEDIA_IMAGES`/`READ_MEDIA_VIDEO`/`READ_MEDIA_VISUAL_USER_SELECTED` into the manifest. **Lesson: after adding a native dependency that ships a config plugin, prefer a full `android/`/`ios/` regeneration over trusting the incremental prebuild, at least until this is verified safe.**
2. **App showed a persistent blank white screen after the rebuild.** Investigated a native `ClassNotFoundException: expo.modules.splashscreen.SplashScreenManager` in logcat first — turned out to be a red herring: `expo-dev-launcher`'s debug code opportunistically looks for `expo-splash-screen` (which this project doesn't install) and already catches the failure internally, just logging it. The real cause was that the **Metro bundler process from an earlier session had silently died** (port 8081 still showed as "Listen" in a stale state, but the server didn't actually respond to HTTP requests). → Killed the stuck `node` processes and started a fresh `npm start`.
3. **Verifying the permission-request flow** — since permissions had gotten into a confusing state during the debugging above, permissions were force-revoked via `adb shell pm revoke com.delpic.app android.permission.READ_MEDIA_IMAGES` (and `_VIDEO`) plus `adb shell am force-stop`, then the app was reopened to confirm a real OS permission dialog appears and grants correctly. `READ_MEDIA_VISUAL_USER_SELECTED` can't be revoked this way (not a directly grantable runtime permission via `pm revoke` on this OS version) — that's expected, not an issue.

**Checkpoint:** Real photos/videos from the device load in reverse-chronological order, correctly rendered; permission request flow verified end-to-end after a revoke + reopen. ✅

## Milestone 3 — Static swipe deck + session persistence

**What was done**
- Installed `react-native-mmkv` (v4 — now built on **Nitro Modules**, a newer native-module framework, not the classic JSI-class API this milestone was originally planned around) and its required peer dependency `react-native-nitro-modules`, plus `zustand` and `expo-splash-screen`.
- Built `src/store/`: `mmkvStorage.ts` (a single `createMMKV({...})` instance wrapped as a Zustand `StateStorage`), `useAppStore.ts` (combined store via the Zustand slices pattern under one `persist(...)`), `sessionSlice` (`cursorIndex`, `lastReviewedAssetId`), `settingsSlice` (`autoplayVideos`, `muteByDefault`, `hapticsEnabled` — not wired to UI yet).
- Gated `app/_layout.tsx` behind store hydration (`useAppStore.persist.hasHydrated()` / `onFinishHydration`), holding the native splash screen via `expo-splash-screen` until hydration completes, to avoid ever flashing the wrong initial state.
- Built the static 3-card stack: `useCardStack` (pagination + visible window + `advance()`/`goBack()`), `SwipeDeck`, `SwipeCard` (scale/offset by stack position, no gestures yet), `CardMedia` (photo via `expo-image`; video shows a placeholder + duration, real playback is Milestone 5).
- Retired the Milestone 2 debug grid — the Deck tab now renders the real (if still static) card stack.
- Added a small back/undo-lite button (top-left) per user request during testing — decrements the cursor. This isn't full Undo yet (there's no trash queue to restore from until Milestone 4/6), just cursor rewind.

**Problems hit & fixes**

1. **`expo-media-library` API redesign, again confirmed for the DX pattern** — no new issue here, but worth noting: reading a package's own shipped `.d.ts` files directly (rather than trusting doc summaries or memory) caught the `react-native-mmkv` v4 Nitro Modules rewrite (`createMMKV()` instead of `new MMKV()`) before it caused a build failure. **This is now the standing approach for every new dependency on this project** — check the installed types first.
2. **Persistent blank white screen after adding the store/splash-screen dependencies** — this one turned out to be a false alarm: Metro was genuinely still compiling. A first request for a fresh/invalidated bundle on this project (~9.8 MB) took close to 3 minutes to compile before the phone got anything back. Confirmed by directly requesting the bundle URL from the PC with a long timeout — it eventually returned 200 OK. **Lesson: after any native rebuild, give the very first JS load significantly longer than it "feels like it should take" before assuming something's broken — check `Invoke-WebRequest http://localhost:8081/status` responds at all before digging further.**
3. **Cards rendered full-bleed with no margin, rounded corners, or safe-area inset** — root cause was two-fold: (a) the Deck screen had stopped using the `Screen`/`SafeAreaView` wrapper when the real `SwipeDeck` replaced the debug grid, so content rendered under the status bar; (b) `SwipeCard` wrapped its content in a `Pressable` *and* an inner `View`, both independently sized via `width: '100%', height: '100%'` — this double absolute-positioned nesting didn't measure correctly on Android. → Simplified to a single `Pressable` per card using `StyleSheet.absoluteFill` (not the `width/height: '100%'` pattern), and reintroduced `SafeAreaView` around the whole deck. Note: this RN/TS version's types only expose `StyleSheet.absoluteFill` (a ready-to-use style), not the older `absoluteFillObject` (a spreadable plain object) — pass it as its own array entry instead of spreading it into `StyleSheet.create`.
4. **Back button felt disconnected, floating above the card** — it was absolutely positioned inside the safe-area padding, outside/above where the card's margin actually started. → Gave the button a dedicated fixed-height header row (52px) directly above the card stack instead of absolute-positioning it independently; this also naturally shrinks the card a little, which was the preferred fix.

**Checkpoint:** Static 3-card stack renders real photos/videos with correct spacing/safe-area; tapping the top card advances the cursor; cursor position survives a full app close + relaunch. ✅

## Milestone 4 — Gestures, spring animation, trash queue, undo

**What was done**
- Added `trashSlice` (`stagedAssets`, `addToTrash`/`removeFromTrash`/`clearTrash`) and extended `sessionSlice` with a capped `history` ring buffer (`recordSwipe`/`popHistory`, `MAX_UNDO_HISTORY = 10`) for real Undo.
- Built `useSwipeGesture`: a `Gesture.Pan()` driving `translateX`/`translateY` shared values, fling/distance thresholds (`SWIPE_VELOCITY_THRESHOLD`, `SWIPE_DISTANCE_RATIO`), spring physics for both the fling-off and snap-back (`lib/animatedConfig.ts`).
- Built `CardOverlay` — a colored border (green/red) that fades in with drag distance, replacing an earlier badge-style design per feedback.
- Rewrote `SwipeCard` to be gesture-driven (rotation via `interpolate`, `GestureDetector`), and `SwipeDeck` to orchestrate real swipe actions (`completeSwipe`/`undo` from `useCardStack`) instead of tap-to-advance.
- Added `ProgressBar` (reviewed/loaded count) to the deck header.
- Added a real "Restart from Beginning" action to the Settings screen (`resetSession()` + `clearTrash()`, with a confirmation dialog) — both to fulfil the plan's Milestone-9 feature early per user request, and because it turned out to be a genuinely useful debugging tool during this milestone's own testing.

**Problems hit & fixes** — this milestone had by far the most iteration, mostly around getting swipe responsiveness and animation lifecycle right:

1. **Snap-back overshot past center to the opposite side before settling** — the snap-back spring was underdamped (damping 18 vs. stiffness 220, well below critical damping). → Increased damping to 32 (critically damped) and added `overshootClamping: true`, which explicitly prevents the value from ever crossing the target.
2. **A visible "flash" when the buried card underneath got promoted** — cards used a *static* (non-animated) transform for stack position, so promoting position 1→0 jumped instantly instead of transitioning. Fixed with an animated `stackPositionSV` + `withTiming`, but this was later made moot: **per user preference, the whole scale/offset-by-position effect was removed entirely** — buried cards now render at the exact same size/position as the top card, distinguished only by z-order (much simpler, and the "flash" complaint became moot along with it).
3. **The core responsiveness problem: swipes were throttled to animation duration.** The data model only advanced once the fly-off spring's `finished` callback fired (250–500ms), so a second swipe within that window was simply ignored — directly conflicting with the requirement to support swipes well under 100ms apart. → Decoupled the two: `completeSwipe` now fires **immediately** on gesture release (via `runOnJS`, before the spring even starts), and the fly-off spring plays out independently and purely visually.
4. **Decoupling the animation from the data model meant the departing card would otherwise vanish/pop instead of visibly flying off** (it was removed from `visibleAssets`, hence unmounted, well before its own exit spring had time to visually complete). → Added an "exiting cards" ghost layer in `SwipeDeck`: a card that's just been swiped keeps rendering — **same component instance, same key** — merged into one single flat keyed list with the active stack, until its own spring's `finished` callback (now used only for cleanup, never for gating) removes it.
5. **Duplicate React key warning + an intermittent forced delay before the next swipe would register under rapid swiping.** Root cause: the `Gesture.Pan()` object was being recreated on every render (gesture-handler's own docs warn about this) because its callbacks closed over per-render props/state. Recreating the native gesture recognizer on every render of a rapidly-updating component could occasionally leave two recognizer instances alive briefly, double-firing the release handler. → Memoized the gesture with `useMemo`, keyed only on `enabled`; callbacks are read through refs (updated every render) so the memoized gesture never goes stale without needing to be rebuilt. Also added defensive dedupe guards in `SwipeDeck`'s render-list construction regardless (an asset can never appear twice, and the "exiting" and "stack" groups are mutually exclusive by construction) — belt and suspenders.
6. **After "Restart from Beginning" (or a fast undo), a card would get stuck completely unresponsive, oversized-looking, covering the whole screen including the header/back button.** Root cause: a card's `translateX`/`translateY` shared values are tied to its component instance, which is deliberately *preserved* across the "exiting → back in the stack" transition (see #4) for animation continuity. But if a card gets pulled back into the visible stack (session reset, or undo) *before* its own exit-fly-off spring finished, those shared values were still wherever the fly-off had left them (e.g. far off-screen) instead of centered — and since it's now rendered as a normal, non-gestured stack card, nothing was driving it back. → `SwipeCard` now tracks its previous `stackPosition` and snaps `translateX`/`translateY` back to `0` specifically on the "was exiting, now back in the stack" transition — never on the transition *into* exiting, which would have broken the real fly-off animation.
7. **Diagnosing "the card underneath never seems to change" turned out to require an actual measurement, not more guessing** — a temporarily-added on-screen debug label (`pos {stackPosition} · {asset.filename}`) confirmed the underlying data/props were correct all along; what the user was actually hitting was problem #6 above (a stuck stale-position card from restart/undo testing). Removed once confirmed. **Lesson: when a UI bug report is ambiguous between "data is wrong" and "rendering is wrong," a cheap on-screen debug label settles it faster than reasoning about it.**
8. **Metro/adb reverse tunnel dropped after the adb daemon restarted mid-session** (unrelated trigger — running `adb logcat` after a period of inactivity respawned the daemon), breaking `localhost:8081` from the dev client. → `adb reverse tcp:8081 tcp:8081` re-establishes it; added to the README troubleshooting list as something to check whenever the dev client suddenly can't reach Metro after previously working.

**Checkpoint:** Swiping right/left keeps/stages-for-trash with a colored border overlay tracking drag distance, spring physics feel snappy with no overshoot, consecutive rapid swipes (well under 100ms apart) are not throttled, Undo restores both the cursor and any trashed item, and progress/undo state persist correctly through a session reset. ✅

## Milestone 5 — Video engine

**What was done**
- Installed `expo-video` and added it to `app.config.ts`'s plugin list. Since this is a new native module, regenerated `android/` from scratch and rebuilt (`npx expo run:android`) rather than trusting an incremental prebuild, per the lesson learned in Milestone 2.
- Added `src/components/deck/VideoCardPlayer.tsx`: wraps `useVideoPlayer`/`VideoView` from `expo-video`, looping, defaulting `muted` from `settingsSlice.muteByDefault`, auto-playing on creation only if `settingsSlice.autoplayVideos` is true, with a manual mute/unmute toggle button overlaid bottom-right.
- Updated `CardMedia` to take an `isActive` prop: video assets only mount a real `VideoCardPlayer` when `isActive` (i.e. `stackPosition === 0`); buried/exiting video cards keep showing the static play-icon + duration placeholder from Milestone 3. `SwipeCard` passes `isActive={stackPosition === 0}`.
- Deliberately did **not** add any new pause/lifecycle logic beyond this mount gating: since `completeSwipe` already advances the cursor immediately on release (Milestone 4), a swiped-away video card's `stackPosition` becomes `-1` (exiting) in the very same update, so `isActive` goes false and `VideoCardPlayer` unmounts — releasing the native player — right as the decision is made, satisfying "pause on decision" and "one video active at a time" for free from the existing architecture instead of needing an explicit play/pause effect keyed on swipe state.

**Problems hit & fixes**

1. Adding `expo-video`'s config plugin to an existing `android/` required a full regeneration (same class of issue as Milestone 2's manifest permissions) — deleted `android/` and rebuilt from scratch via `npx expo run:android` rather than risk an incomplete incremental prebuild.

**Checkpoint:** Confirmed on-device — videos autoplay muted on the active card, the mute/unmute toggle works, and playback stops immediately on swipe (via unmount) with no audio bleed between cards. ✅
